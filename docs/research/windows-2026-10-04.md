# Founder-observed Windows experiments: 2026-10-04

## Provenance and limits

**Evidence category:** reported actions, procedures, and results in the WIN records are founder-observed experiments, not independently reproduced by Workspace Doctor during M0 and not official product guarantees. Limitations state what the evidence does not establish. Paragraphs labeled **Design implication** are Workspace Doctor prescriptions or interpretations, not founder-observed behavior.

All records use [baseline B0](../compatibility.md#baseline-context-b0): Windows/native Codex Desktop local context; desktop version, agent version, Windows build, and exact timing are unknown. The reported SQLite filename is `state_5.sqlite`; no full schema was provided. No private artifacts were inspected during M0.

All identifying paths, titles, IDs, marker values, and prompt-derived folder names below are synthetic replacements. Experiments 1-14 are summarized observations; detailed procedures and sample counts were not supplied. Experiments 15-17 include a richer reported sequence. Missing details must not be invented.

<a id="win-001"></a>
## WIN-001: Local Project identity and folder identity

**Reported result:** a Local Project and its filesystem folder are distinct identities. Their appearance and lifecycle need not coincide.

**Limit:** no universal mapping cardinality or identifier algorithm was established.

**Design implication:** preserve app and filesystem observations separately.

<a id="win-002"></a>
## WIN-002: Projectless thread with real CWD

**Reported result:** a thread could have no Local Project assignment while using an existing directory as CWD.

**Limit:** this observation does not establish a universally reliable membership field.

**Design implication:** establish projectlessness through appropriate assignment evidence, not merely a null database field. Projectlessness is not inherently a problem.

<a id="win-003"></a>
## WIN-003: Several main threads sharing a workspace

**Reported result:** multiple main threads could share the same workspace/folder.

**Limit:** the term main thread reflects the founder's classification; general discriminators remain unknown.

**Design implication:** a shared path must not be treated as proof of duplicated conversations, accidental sharing, or a need to move files.

<a id="win-004"></a>
## WIN-004: Different project ID namespaces

**Reported result:** Local Project IDs in global state and project IDs in SQLite were not necessarily equal for corresponding roots.

**Limit:** a unique cross-source identity correspondence was not established.

**Design implication:** root normalization and other evidence may support reconciliation, but matching roots alone do not establish a unique project identity. Never join different namespaces by ID alone.

<a id="win-005"></a>
## WIN-005: Null SQLite project ID despite UI membership

**Reported result:** `threads.project_id` in `state_5.sqlite` was often null even where the UI showed Local Project membership.

**Limit:** no frequency estimate or complete dataset was supplied; this does not prove that the field has no useful meaning.

**Design implication:** do not interpret a null SQLite project ID as projectless.

<a id="win-006"></a>
## WIN-006: Global-state assignments matched the UI

**Reported result:** `thread-project-assignments` in `.codex-global-state.json` corresponded more closely to visible assignments than SQLite project IDs in the observed dataset.

**Limit:** this is comparative evidence for that dataset, not an eternal source-of-truth hierarchy.

**Design implication:** validate freshness, completeness, and semantics before preferring assignment evidence on another build.

<a id="win-007"></a>
## WIN-007: Permanent thread deletion and metadata lag

**Reported action:** use the thread UI's Permanently delete action.

**Reported result:** the SQLite thread row and `session_index` entry disappeared immediately. Assignment metadata could remain until the associated Local Project was removed.

**Limit:** timing is qualitative; the founder did not provide a complete artifact/dependent-record inventory.

**Design implication:** surviving references must not be treated as immediate proof of corruption, nor missing rows as proof that every artifact was erased.

**Founder-reported supporting supplement — added 2026-10-04, experiment date 2026-10-04:** supplied by the founder in the Founding Knowledge Gap Audit corrections. Permanent deletion removed the selected visible thread's SQLite row and `session_index` entry. Unrelated internal Guardian records sharing its workspace could remain; shared CWD did not establish that they were dependents of the deleted thread. Assignment references were observed after thread deletion and were later absent after Project removal. Cleanup timing, causality, and whether the references would have disappeared later without Project removal were not established.

<a id="win-008"></a>
## WIN-008: Removing a Local Project

**Reported action:** remove a Local Project through the UI.

**Reported result:** the app project was removed, files and existing chats remained, and associated assignment references were cleaned in the experiment.

**Limit:** the exact cleanup boundary and timing were not measured.

**Design implication:** do not reinterpret project removal as filesystem deletion or chat deletion.

**Founder-reported supporting supplement — added 2026-10-04, experiment date 2026-10-04:** supplied by the founder in the Founding Knowledge Gap Audit corrections. Assignment references seen after thread deletion were later absent after Project removal. The original word "cleaned" records that observed sequence, not established cleanup timing or causality; disappearance without Project removal was not tested. See the [WIN-007 supplement](#win-007) and [cleanup research question](open-questions.md#q-15).

<a id="win-009"></a>
## WIN-009: Internal records survived visible cleanup

**Reported result:** records characterized by the founder as Guardian/subagent rows remained after visible threads, projects, worktrees, and folders were gone. They could have null project IDs, no `thread_spawn_edges`, and nonexistent CWDs.

**Limit:** general classification and retention semantics were not established.

**Design implication:** do not infer internal status from these attributes alone, or call remaining records corrupt/safe to delete.

**Founder-reported supporting supplement — added 2026-10-04, experiment date 2026-10-04:** supplied by the founder in the Founding Knowledge Gap Audit corrections. Unrelated internal Guardian records could share the workspace and remain after the selected visible thread's row and index entry were deleted. Shared CWD did not establish a dependent relationship to that thread. This does not expand the reported deletion scope to every record using that directory.

<a id="win-010"></a>
## WIN-010: Managed worktree removal through Codex

**Reported action:** remove a Codex-managed worktree using the official Worktrees UI.

**Reported result:** both the physical managed directory and Git's worktree registration were removed.

**Limit:** this does not establish retention of ignored files, universal recoverability, behavior for externally managed worktrees, or every build's UI flow.

**Design implication:** prefer the owning application's supported lifecycle rather than direct directory deletion.

<a id="win-011"></a>
## WIN-011: Thread navigation and CWD-copy actions

**Reported result:** `codex://threads/<thread-id>` provided useful thread navigation; the UI exposed Copy deeplink and Copy working directory.

**Limit:** a useful link does not guarantee future retention, link stability on every surface, or immediate runtime alignment. The placeholder is not a real ID or a functioning example link.

**Design implication:** treat deeplinks as optional navigation and copied CWD as separate evidence from runtime location.

<a id="win-012"></a>
## WIN-012: Extended Windows path prefix

**Reported result:** SQLite CWDs could contain the extended prefix `\\?\C:\...`.

**Synthetic illustration:** `\\?\C:\Synthetic\atlas` may need comparison with `C:\Synthetic\atlas`.

**Limit:** general namespace equivalence was not tested.

**Design implication:** normalization must preserve semantics, including extended UNC and unusual namespace cases; do not universally strip the prefix.

<a id="win-013"></a>
## WIN-013: Nested Local Projects

**Reported result:** a parent directory and its child could independently be Local Projects.

**Synthetic illustration:** `C:\Synthetic\atlas` and `C:\Synthetic\atlas\drafts` each have a project identity.

**Limit:** project membership precedence was not established by this observation.

**Design implication:** containment alone must not be treated as a defect or membership rule. Avoid automatically assigning threads to the nearest ancestor.

<a id="win-014"></a>
## WIN-014: Thread survives removal of its Local Project

**Reported result:** a thread could continue as projectless after its Local Project was removed.

**Limit:** this does not establish every thread type's retention or the removal of every historical reference.

**Design implication:** do not equate project removal with thread loss.

<a id="win-015"></a>
## WIN-015: External CWD rename and replacement workspace

**Reported procedure, with synthetic values:**

1. Create `C:\Synthetic\workspaces\cwd-probe-a` containing `probe.txt` with `SYNTHETIC_MARKER_ALPHA`.
2. Use it as a projectless thread's CWD.
3. Close Codex and externally rename the directory to `cwd-probe-b`.
4. Restart Codex, open the thread, and inspect its working directory.
5. Send a new turn while the old directory is absent.

**Reported result:** SQLite retained the old path after rename, restart, and thread opening. Copy working directory also retained it. A new turn did not discover the renamed folder. Codex instead created a prompt-derived workspace under a dated directory and persisted that replacement CWD.

The invented fallback `C:\Synthetic\workspaces\2026-10-04\replacement-workspace` describes the shape only; it is not an observed path or the original prompt-derived name.

**Limit:** one reported probe sequence does not establish behavior for every release, project-assigned thread, filesystem, rename type, or missing-path cause. The replacement was not the renamed destination.

**Design implication:** warn about the recorded risk before continuing a missing-CWD thread; do not predict fallback creation as certain.

**Founder-reported supporting supplement — added 2026-10-04, experiment date 2026-10-04:** supplied by the founder in the Founding Knowledge Gap Audit corrections. Before the successful closed-app rename above, an external PowerShell rename failed while Codex was running: Windows reported that the folder was being used by another process. After Codex was fully closed, the rename succeeded. The responsible process/handle was not identified.

**Supplement limit:** this sequence does not establish which process held the folder or that Codex always locks workspace folders.

<a id="win-016"></a>
## WIN-016: Temporary Local Project as migration bridge

**Reported continuation of WIN-015, with synthetic values:**

1. Open `C:\Synthetic\workspaces\cwd-probe-b` through File → Open Folder → Trust folder, creating a Local Project.
2. Assign the existing thread through its Project context-menu action.
3. Inspect Copy working directory immediately after assignment.
4. Send a new turn and verify the runtime directory and marker file.
5. Inspect persisted metadata, then remove the temporary Local Project.

**Reported result:** assignment alone did not immediately update the copied CWD; it still showed the previous/fallback directory. During the subsequent successful turn, runtime CWD was the renamed destination and the marker was read. Afterward, copied CWD and SQLite CWD showed the destination, and global assignment referenced the new project. Removing that project left the thread projectless with destination CWD retained.

**Limit:** persistence was observed after successful execution, not proven to occur merely on assignment or any next turn.

**Design implication:** treat the bridge as experimental guidance, not an officially guaranteed migration API. A verification turn can execute tools and change Codex state; assignment alone is not migration completion.

**Founder-reported supporting supplement — added 2026-10-04, experiment date 2026-10-04:** supplied by the founder in the Founding Knowledge Gap Audit corrections.

- **Measurement timing:** immediately after assignment to the destination Local Project, only Copy working directory was checked; it still showed the previous path. SQLite stored CWD was not checked at that point. During the subsequent successful turn, runtime CWD was the destination. Afterward, Copy working directory and SQLite stored CWD showed the destination. Persistence was observed after the successful turn; the exact persistence mechanism or trigger was not established.
- **UI route:** the Project assignment action was found in the thread context menu in the Recents/list view. It was not visible in the in-thread menu used during this experiment. This is procedural evidence for that build/UI context, whose exact version remains unknown, not a universal menu-availability claim.

<a id="win-017"></a>
## WIN-017: Second migration to a descriptive folder

**Reported procedure, reconstructed with synthetic identifying values:** a projectless thread named `Synthetic Atlas Notes` used `C:\Synthetic\workspaces\2026-01-02\historical-workspace`. Its folder was moved to `C:\Synthetic\workspaces\atlas-notes`. The destination was opened as a Local Project, the existing thread was assigned, and a verification turn was sent.

**Reported result:** runtime CWD, SQLite CWD, copied working directory, and Local Project root all matched the destination; the old path no longer existed. Migration succeeded without directly editing SQLite or JSON.

**Limit:** this provides a second founder-reported success, not independent reproduction or coverage of shared workspaces, managed worktrees, failures, every file type, or later releases. Removal of the bridge project in this second case was not supplied as a result and is not inferred.

**Design implication:** revalidate the bridge for a target environment before calling it validated there; two founder successes do not establish universal migration safety.

## Interpretation: design decisions

Keep stored CWD, assignment, and runtime evidence separate. Preserve internal/unclassified records. Qualify absence by coverage and accessibility. Document why each proposed rule exists and what would narrow or retire it.
