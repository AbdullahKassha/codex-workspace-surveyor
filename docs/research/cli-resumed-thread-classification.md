## WIN-022: Desktop-visible Thread with no assignment observed

**Founder-observed report, received 2026-10-16:** one exact nominated Thread appeared normally in Codex Desktop with a matching deeplink and stored working directory. Workspace Surveyor displayed `no-assignment-observed` membership, `unknown` visibility, a **Needs review** row, instruction locations not checked, and a title resolved from the session index. The reported CWD was the user-profile directory, outside the selected nested discovery root. Private identifiers, title and path spellings are deliberately omitted.

**Correction incorporated:** the founder supplied `& $cli.FullName --no-daemon resume --all` as the actual invocation. The earlier claim that this invocation created the Thread is withdrawn; the earlier `#` was a transcription error. Launch directory, stored CWD and creation/resumption history are separate observations. The report does not establish which session was selected, which directory choice was made, the original creator, or whether this invocation changed anything. Execution time, CLI/Desktop versions, Windows build and metadata acquisition timing are unknown. This is one naturally encountered case, not an experiment establishing behavior for all CLI Threads.

**Investigation boundary:** local HEAD matched the founder's accepted baseline `3fdc111777e19c5919a8b5c5f0cc8e3635410511`; the worktree was initially clean. Only repository implementation/evidence, the supplied report, current official documentation and invented fixtures were used. No personal Codex source, live original SQLite database, transcript body, unrelated Thread, process or recovery slot was inspected. The reported UI values were not independently remeasured.

## Conclusion and remaining uncertainty

**Design assessment:** the supplied values are consistent with correct conservative classification. WIN-022 demonstrates a coverage limit: a Desktop-visible record can lack the corroboration Surveyor requires for ordinary Workspace eligibility. `unknown` accurately preserves that limit. It does not contradict the founder's visibility observation. The current UI says membership is unknown, keeps the record reviewable, and reports instruction checks as unperformed; no demonstrated presentation defect requires a change. Classification, UI, acquisition, source protection, recovery and Codex data remain unchanged. No new CLI-specific classification or adapter is introduced.

**Unknown:** actual exact-ID registry presence/absence, source/archive values, freshness across sources, earlier creation/resumption history and any CWD transition remain unverified. There is no demonstrated new metadata shape to decode. Repository evidence and the supplied classifications suffice to explain this result, so additional personal inspection is unnecessary for this conclusion. Any later exact-Thread verification needs a separately proposed bounded read-only procedure and founder approval; the supplied invocation alone must never be used to fill these gaps. Metadata alone may still be unable to recover history without bodies, which remain excluded.
